# Mappa del repository

## Scopo

Questa è la mappa di orientamento del repository.

Usarla per individuare il confine corretto prima di modificare codice o preparare contesto per un'API AI. Non contiene contratti HTTP completi, regole di dominio o dettagli di implementazione.

La mappa distingue codice applicativo, dati runtime, persistenza canonica, journal sidecar, frontend, script operativi e documentazione owner.

## Runtime locale

```txt
python avvio.py
  ↓
launcher/
  ├─ CDP
  │   └─ endpoint valido riusato oppure Chrome dedicato su porta libera
  ├─ backend
  │   └─ backend/src/server.js
  └─ frontend
      └─ node frontend/node_modules/vite/bin/vite.js
  ↓
browser aperto sull'URL frontend effettivo
```

| Porta preferita | Servizio        | Regola                                                                                                                                                                                                  |
| --------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `9222`          | Chrome CDP      | Un endpoint valido viene riusato. Se assente, il launcher avvia Chrome dedicato su una porta libera. Chrome/CDP, riusato o avviato dall’helper, non viene registrato come owned né chiuso dal launcher. |
| `3001`          | Backend Express | Usa `process.env.PORT`, con default `3001`; il launcher riusa solo un backend con identità Tennis Decision UI o sceglie una porta alternativa.                                                          |
| `3000`          | Frontend Vite   | Vite viene avviato tramite Node e CLI locale su `127.0.0.1`; il launcher usa una porta alternativa se necessario.                                                                                       |

Le porte sono preferite, non riservate.

Il launcher non termina processi in base alla sola porta. Registra come owned soltanto backend e frontend avviati dalla sessione corrente. I processi riusati restano esterni alla ownership; Chrome/CDP, riusato o avviato dall’helper, non viene registrato come owned né chiuso dal launcher.

Il launcher non è owner del journal di persistenza. Non ripara, non cancella e non compatta `pending_commits`.

## Persistenza canonica e journal

La persistenza canonica vive sotto `backend/match_history/`.

```txt
backend/match_history/
├── <eventId>/
│   ├── history*.json
│   ├── timeline*.json
│   └── pending_commits/
│       └── *.json
└── ...
```

| Area                       | Regola di orientamento                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------- |
| History aggregate          | Stato canonico aggregato; non modificare manualmente                                   |
| Timeline append-only       | Sequenza canonica degli eventi; non modificare manualmente                             |
| `pending_commits/`         | Journal sidecar tecnico per commit logici incompleti e recovery                        |
| `commitId`                 | Identificatore logico del commit da propagare fra writer e recovery                     |
| `integrity`                | Stato read-only derivato dalla persistenza incompleta nota                              |
| `partial_persistence`      | Persistenza incompleta osservabile; non equivale a health, freshness o errore scraper   |
| `recovery_failed`          | Recovery non riuscita osservabile; non deve essere nascosta da cleanup o diagnostica     |

Le API read-only possono esporre `integrity`, ma non riparano journal, non scrivono dati canonici e non avviano tracker o scraper.

La documentazione owner è:

```txt
docs/tennis-decision-ui/modules/storage/01-timelines-and-history.mdx
docs/tennis-decision-ui/modules/storage/02-commit-journal-and-recovery.mdx
```

Gli scraper Python non sono owner della persistenza canonica. Producono campioni o diagnostica; la decisione su commit, `repairOnly`, runtime confermato e integrity appartiene al backend.

## Dati runtime, generati e sensibili

| Percorso                                             | Tipo                                      | Regola di orientamento                                                                  |
| ---------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------- |
| `backend/match_history/`                             | Timeline canoniche, history e journal     | Non modificare o cancellare fuori da retention, replay o recovery espliciti             |
| `backend/match_history/*/pending_commits/`           | Journal sidecar tecnico                   | Non cancellare manualmente; non includere in cleanup cache o rollback cieco             |
| `backend/scraper_cache/`, `backend/betfair_cache/`   | Cache runtime                             | Non sono fonti canoniche; pulizia consentita solo tramite utility allow-list            |
| `backend/scraper_profile/`                           | Profilo browser SofaScore                 | Escludere da contesto AI e condivisione                                                 |
| `backend/betfair_network_dump/`                      | Dump diagnostici opzionali                | Redatti ma potenzialmente sensibili; non usare come input algoritmico o fonte canonica  |
| `backend/*_debug.log`, `backend/betfair_scraper.log` | Log runtime                               | Diagnostica soltanto                                                                    |
| `launcher/.runtime/`                                 | Lock e manifest effimeri                  | Non modificare manualmente durante una sessione attiva                                  |

Per un task ristretto, escludere di default:

```txt
node_modules
timeline e history runtime
pending_commits
cache
profili browser
dump diagnostici
log
lockfile e manifest runtime
file con segreti o credenziali
Repomix completi
```

Usare questi dati soltanto quando il task riguarda esplicitamente storage, retention, replay, diagnostica o recovery.

La utility di manutenzione cache runtime è `scripts/cleanup_runtime_cache.py`. Opera solo sulle cache allow-list e non deve essere trattata come cleanup generico del repository.

La utility di cleanup non deve cancellare history, timeline o `pending_commits`.

## Regole di orientamento

* Modifica un endpoint: leggere il router interessato, il modulo puro estratto, il relativo test e il documento API owner.
* Modifica polling: leggere `matchTracker.js` o l'hook frontend specifico, non l'intero progetto.
* Modifica `localContext`: leggere `normalizeSnapshot.js`, `pointByPoint.js`, `localContext.js`, i test collegati e il consumer frontend soltanto quando cambia il rendering.
* Modifica Source Identity frontend: leggere `App.jsx`, hook status gate, presentazione pura, componenti Source Identity, test e registro live.
* Modifica Source Identity backend: leggere gate, Evidence, route Match, route Evidence e test collegati.
* Modifica scraping: leggere il wrapper root, il package Python interessato e l'adattatore Node.
* Modifica Graph URL dirette Betfair: leggere `graph_url.py`, `graph_url_test.py` e `scrape.py`; leggere `market_api.py` e `ladder.py` soltanto come contratti da preservare.
* Modifica startup: leggere `avvio.py`, `launcher/` e gli script PowerShell.
* Modifica persistenza canonica: leggere history, timeline, commit journal, recovery e test collegati prima delle API o del frontend.
* Modifica `integrity` o `409 persistence_integrity`: leggere storage, API interessata, Evidence se coinvolta e frontend consumer.
* Modifica cleanup o rollback: leggere prima retention, validation, repository map e commit journal; non trattare `pending_commits` come cache.
* Non usare history, cache, dump, lockfile, `pending_commits` o Repomix completo come contesto iniziale per un task ristretto.
