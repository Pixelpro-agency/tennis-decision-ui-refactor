# Validità tecnica dei campioni Betfair

## Stato

**Implementato, da validare.**

La classificazione tecnica, i guard di persistenza e i test locali sono implementati.

Per il logout Graph esplicito sono stati osservati live: rilevamento del requisito di login, persistenza del tick `status-only`, health `red` con popup e audio, e ritorno a `Connected` dopo il login.

Restano da validare con evidenze dedicate timeout, errore rete/API reale, URL Graph malformate, mismatch `marketId`, mercato Betfair realmente `finished`, failure reali di persistenza journalizzata e recovery dopo riavvio.

Non è archiviato un payload `/latest` post-fix né un test automatico PASS dedicato al tick `status-only`.

## Scopo

Questo documento definisce quando un risultato Betfair può diventare un campione elaborabile.

Distingue:

```txt
errore tecnico
≠
mercato concluso
≠
tick canonico persistibile
```

Un risultato tecnicamente incompleto non deve essere interpretato come fine mercato e non deve generare nuovi dati canonici.

Un risultato tecnicamente utilizzabile non garantisce invece da solo la persistenza: regressioni, duplicati, Source Identity e commit journalizzato vengono controllati successivamente dal flusso timeline.

Un campione tecnico non utilizzabile può solo partecipare al repair di un journal Betfair già pendente tramite percorso `repairOnly`. Questo non equivale a un nuovo campione canonico e non conferma lo stato runtime dei runner.

## Implementazione

```txt
backend/src/sofa/betfair/processor.js
backend/src/sofa/betfair/trackerUpdate.js
backend/src/sofa/betfair/processor/runnerProcessing.js
backend/src/sofa/matchHistory/commitJournal.js
```

`trackerUpdate.js` valuta prima il mercato concluso, poi la validità tecnica.

Il processor applica una seconda protezione prima della persistenza canonica.

Il journal non cambia la classificazione tecnica del campione: coordina commit e repair dopo che il flusso ha stabilito se il campione può produrre nuove scritture o se può solo tentare un repair pendente.

## Classificazione tecnica

`classifyBetfairTechnicalSample(...)` restituisce:

```txt
usable
reason
totalMatched
```

Un campione non è utilizzabile quando:

```txt
raw assente o non oggetto
raw.error presente
raw.api_error presente
raw.runners non è un array
raw.runners è vuoto
raw.market_info.total_matched assente
total_matched non numerico o non finito
total_matched minore o uguale a zero
```

Reason stabili:

```txt
invalid_raw
raw_error
api_error
runners_missing
runners_empty
total_matched_missing
total_matched_invalid
total_matched_non_positive
```

Quando il processor riceve un campione non utilizzabile, restituisce un risultato tecnico normalizzato con:

```txt
technicalFailure
```

`total_matched` può essere normalizzato anche da stringhe formattate, ad esempio:

```txt
EUR 74,817
```

## Mercato concluso

Il polling Betfair può fermarsi automaticamente soltanto quando il risultato espone:

```txt
event_status.hasFinished === true
```

Questo controllo avviene prima della classificazione tecnica.

```txt
hasFinished esplicito
→ polling Betfair fermato
→ aggiornamento runtime riuscito
→ nessun passaggio al gate
→ nessuna persistenza del campione conclusivo

campione tecnicamente non utilizzabile
→ errore runtime diagnostico
→ polling resta attivo
→ nessun gate
→ nessuna nuova persistenza canonica
```

Errore fetch, DNS, logout, `api_error`, runner mancanti o `total_matched` non valido non equivalgono a mercato concluso.

Un logout Graph esplicitamente rilevato non equivale a mercato concluso. Può attivare, soltanto più avanti nel flusso di persistenza e alle condizioni ristrette definite per il `regressive_sample`, un tick canonico di sola transizione di stato (`status-only`).

## Invarianti del campione tecnico non utilizzabile

Un campione tecnicamente non utilizzabile:

```txt
non chiama processBetfairRunnerState
non chiama rebindPendingBetfairRunnerState
non chiama commitPendingBetfairRunnerState
non chiama discardPendingBetfairRunnerState
non aggiorna o cancella il baseline marketState
non genera nuovi commit canonici
non genera tick canonici
non salva nuove row history
non salva nuove timeline
non modifica Source Identity
non passa al gate Source Identity
non modifica betfairFinished
```

Il backstop in:

```txt
persistBetfairProcessedResult(...)
```

protegge anche le chiamate dirette.

Per un campione tecnico non utilizzabile, il comportamento ordinario resta uno skip tecnico:

```txt
ok: true
skipped: true
reason: <technical reason>
```

senza eseguire cleanup timeline, history o nuove scritture canoniche.

### RepairOnly

Prima di tornare al comportamento tecnico invariato, un campione Betfair non utilizzabile può tentare il repair di un journal pending tramite:

```txt
persistBetfairTrackingSample(..., { repairOnly:true })
```

Il percorso `repairOnly` non classifica il campione come utilizzabile e non lo trasforma in un nuovo tick.

Con `repairOnly:true`:

```txt
recovered
→ risultato di recovery propagato
→ nessun nuovo tick
→ nessuna nuova row history
→ nessuna mutazione marketState

failure strutturata
→ risultato di failure propagato
→ nessun nuovo tick
→ nessuna nuova row history
→ nessuna mutazione marketState

unchanged
→ comportamento tecnico invariato
→ skip tecnico del campione
```

Il repair usa solo payload, target, metadata e `commitId` già presenti nel journal. Non legge sample live, non ricostruisce dati business, non avvia tracker, scraper o fetch e non passa da Source Identity o Evidence.

Un errore isolato Graph URL non rende da solo inutilizzabile un campione con runner e `total_matched` affidabili. La validazione di Graph URL e ladder appartiene a un contratto separato.

## Campione utilizzabile e persistenza canonica

La classificazione tecnica autorizza il campione a proseguire verso gate e persistenza, ma non garantisce la creazione di un tick canonico.

Dopo la normalizzazione, il sistema può ancora rifiutare il risultato come:

```txt
regressive_sample
duplicate_tick
```

Per `duplicate_tick` e per ogni `regressive_sample` ordinario:

```txt
nessuna nuova history
nessuna nuova timeline
nessun commit del baseline proposto
```

Il commit canonico Betfair è journalizzato e produce un esito strutturato. Solo questi esiti possono confermare lo stato runtime dei runner:

```txt
complete
recovered
```

Esiti incompleti o falliti non confermano `marketState`:

```txt
partial
failed
writer non-ok
writer undefined
target errato
commitId errato
```

Il dettaglio di `commitId`, journal, repair e ordine di scrittura appartiene ai documenti storage.

### Eccezione stretta: logout Graph esplicito

Un `regressive_sample` può produrre un tick canonico `status-only` soltanto quando sono tutte vere le seguenti condizioni:

```txt
esiste un tick Betfair canonico precedente
→ diagnostics.graphLoginRequired = true
→ le Graph URL non hanno prodotto righe ladder
→ il sample è classificato regressive_sample
```

Il tick `status-only`:

```txt
conserva mercato e runner dell’ultimo tick canonico
non adotta quote, volumi, ladder o Money Flow regressivi
viene aggiunto alla timeline canonica
non aggiorna il baseline runner o market
non aggiunge il sample raw regressivo alla history
```

Espone inoltre:

```txt
graphHealth.status = auth_suspected
diagnostics.graphLoginRequired = true
diagnostics.statusOnlyGraphLogin = true
```

Questo permette al runtime health già esistente di produrre `red` e `alert`, senza un nuovo contratto frontend.

L’eccezione non modifica l’authority, la fase o la persistenza del gate Source Identity. Un errore rete/API o un’assenza feed non viene classificato come logout Graph.

## Confini

Questo modulo classifica l’utilizzabilità tecnica del campione Betfair e documenta il comportamento del sample tecnico rispetto a commit e repair.

Non deve:

```txt
dedurre Source Identity
decidere mapping giocatori o runner
dedurre strategia
scrivere contratti HTTP
trattare un errore tecnico come mercato concluso
creare nuovi commit da sample tecnici non utilizzabili
mutare marketState durante repairOnly
decidere retention di cache, dump o log
documentare payload raw o dati sensibili del journal
```

Il gate Source Identity autorizza o blocca la persistenza soltanto dopo che il campione Betfair è stato classificato come tecnicamente utilizzabile.

Un repair `repairOnly` non passa dal gate, perché non è un nuovo campione live da autorizzare: è la riparazione deterministica di un commit già journalizzato.

## Verifica

Dalla cartella `backend/src`:

```txt
node --check sofa/betfair/processor.js
node --check sofa/betfair/trackerUpdate.js
node --check sofa/betfair/processor/runnerProcessing.js

node sofa/betfair/processor.test.mjs
node sofa/betfair/trackerUpdate.test.mjs
node sofa/betfairFetch.test.mjs
```

Copertura attuale:

```txt
processor.test.mjs
→ classificazione runners_empty
→ duplicate_tick senza history o timeline
→ regressive_sample senza history o timeline
→ persistenza di una modifica materiale
→ commit Betfair strutturato
→ repair pending senza nuovo tick
→ sample tecnico senza mutazione marketState

trackerUpdate.test.mjs
→ hasFinished senza gate o persistenza
→ campioni tecnici senza gate o nuova persistenza
→ polling attivo dopo errori tecnici
→ ripresa con campione valido
→ runtime health dopo errore e recupero

betfairFetch.test.mjs
→ propagazione di risultati structured dal processor
→ separazione tra errore tecnico, sample valido e commit
```

Il guard di persistenza per un campione tecnico è presente nel codice. Se viene modificato `persistBetfairProcessedResult(...)`, deve restare coperto da un’asserzione diretta dedicata al percorso tecnico e al percorso `repairOnly`.

Per l’eccezione `status-only`:

```txt
test automatico PASS dedicato
→ non archiviato

script Node mirato
→ non valido come test, perché l’here-doc era corrotto
→ non dichiarare PASS

osservazione live manuale
→ logout Graph
→ health red, popup e audio
→ login ripristinato
→ ritorno a Connected
```

I normali test su `regressive_sample` restano validi per i sample regressivi ordinari: non coprono da soli l’eccezione logout Graph.
