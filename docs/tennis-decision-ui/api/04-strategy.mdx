# API Strategy

## Scopo

Questo documento definisce il contratto HTTP del router:

```txt
backend/src/routes/strategy.js
```

L’endpoint attuale espone il view model della strategia Lay The Winner.

Non è un endpoint di tracking e non modifica timeline o history. Legge la timeline Betfair persistita e costruisce un’analisi SofaScore per comporre il view model.

## Endpoint

```txt
GET /api/strategy/lay-the-winner?url=<sofascoreMatchUrl>
```

La query `url` è obbligatoria.

## Flusso

```txt
query url
→ normalizeLayTheWinnerRequest
→ extractEventId
→ buildSofaAnalysis(eventId)
→ loadTimeline('betfair', eventId)
→ buildLayTheWinnerViewModel
→ risposta JSON
```

`buildSofaAnalysis(eventId)` centralizza l’analisi SofaScore.

Il router aggiunge logging diagnostico e compone il view model finale. Il logging non modifica il contratto JSON dell’endpoint.

## Risposta riuscita

La risposta è un view model pronto per il client.

Schema top-level:

```json
{
  "app": {
    "tabs": []
  },
  "header": {
    "competition": "<testo>",
    "status": "<LIVE o stato SofaScore>",
    "matchTitle": "<home> vs <away>",
    "set": null,
    "gameScore": null,
    "serving": null,
    "connections": {}
  },
  "strategy": {
    "id": "lay_the_winner",
    "name": "Lay the Winner",
    "speed": "SLOW",
    "available": false,
    "reason": "legacy_signal_unavailable",
    "decision": {},
    "entryRules": [],
    "successProbability": {},
    "setupContext": [],
    "strategyChecklist": [],
    "marketEvidence": {}
  },
  "footerHints": {}
}
```

Comportamento corrente:

```txt
strategia legacy
→ non disponibile

decision.signal
→ UNAVAILABLE

successProbability
→ non disponibile perché TOT non implementato

marketEvidence
→ resta disponibile come contesto separato
```

`header.status` diventa `LIVE` quando lo stato SofaScore è `inprogress`. Negli altri casi usa lo stato SofaScore disponibile oppure `—`.

Il router non produce una decisione operativa, non assegna un’azione di trading e non attribuisce causalità tra campo e mercato.

## Errori di input

| Caso                | Status | Body                                                      |
| ------------------- | ------ | --------------------------------------------------------- |
| URL assente o vuoto | `400`  | `{ error: 'URL mancante. Usa ?url=<sofascoreMatchUrl>' }` |
| URL senza event ID  | `400`  | `{ error: 'URL non valido o eventId non trovato' }`       |

Per input non valido, il router termina prima di eseguire analisi SofaScore, letture Betfair, tracking, scraper, browser o stop.

## Mapping errori runtime

| Errore ricevuto                   | Status |
| --------------------------------- | ------ |
| Messaggio con `404` o `not found` | `404`  |
| Messaggio con `403` o `blocked`   | `503`  |
| Qualunque altro errore            | `500`  |

Il controllo `403` o `blocked` ha priorità quando un messaggio corrisponde a più condizioni.

Il comportamento attuale restituisce il messaggio dell’errore nel body:

```json
{
  "error": "<messaggio>"
}
```

Il frontend non deve dipendere dal testo completo dell’errore come contratto stabile.

## Confini

`layTheWinnerResponse.js` deve restare puro.

Non deve eseguire:

* fetch SofaScore;
* letture timeline;
* tracking;
* scraper;
* browser;
* persistenza;
* logging.

Il router conserva gli effetti collaterali. Il modulo puro conserva validazione della richiesta e mapping HTTP.

La costruzione del contesto strategico e del market evidence resta nei moduli Strategy dedicati. Il router non deve ricostruirne la logica.

## Verifica

Dalla cartella `backend/src`:

```txt
node --check routes/strategy.js
node --check routes/strategy/layTheWinnerResponse.js
node routes/strategy/layTheWinnerResponse.test.mjs
node routes/strategy/layTheWinnerRoute.test.mjs
```

Smoke test sicuro:

```txt
GET /api/strategy/lay-the-winner
```

Deve restituire `400` senza eseguire analisi SofaScore, lettura Betfair, scraper, browser, tracking o stop.
