# Convenzioni documentazione

## Scopo

Questo documento definisce le convenzioni per scrivere, collocare, aggiornare e verificare la documentazione tecnica canonica del progetto.

Ogni documento deve essere:

```txt
specifico
→ piccolo
→ aggiornabile
→ collegato al suo modulo
→ adatto a un contesto API mirato
```

La documentazione non deve diventare una copia integrale del codice.

Deve spiegare responsabilità, confini, contratti, invarianti, stato e verifica.

## Fonte canonica

La documentazione canonica è organizzata sotto:

```txt
docs/tennis-decision-ui/
```

I nuovi documenti seguono questa struttura:

```txt
architecture/
api/
modules/
operations/
ai/
roadmap/
reference/
```

| Area            | Responsabilità                                   |
| --------------- | ------------------------------------------------ |
| `architecture/` | Confini e flussi di sistema                      |
| `api/`          | Contratti HTTP                                   |
| `modules/`      | Comportamento e invarianti dei moduli            |
| `operations/`   | Avvio, controllo, diagnostica e rollback         |
| `ai/`           | Regole per contesto AI e convenzioni documentali |
| `roadmap/`      | Funzionalità pianificate                         |
| `reference/`    | Mappe e riferimenti del repository               |

## Una responsabilità per file

Ogni file deve avere un solo owner logico.

| Area o responsabilità    | Owner documentale                              |
| ------------------------ | ---------------------------------------------- |
| Contratti HTTP           | `api/`                                         |
| Scheduler live           | `modules/sofa/01-live-tracking.mdx`            |
| Timeline e history       | `modules/storage/01-timelines-and-history.mdx` |
| Source Identity          | `modules/evidence/02-source-identity.mdx`      |
| Avvio e shutdown         | `operations/01-local-runtime.mdx`              |
| Convenzioni AI           | `ai/`                                          |
| Funzionalità pianificate | `roadmap/`                                     |

Un documento può collegare un altro modulo, ma non deve duplicarne l’intero contratto.

Dividere un file solo quando cambia almeno uno tra:

* ownership;
* contratto;
* modulo;
* contesto API necessario;
* verifica richiesta.

## Dimensione consigliata

Target normale:

```txt
200–600 parole
```

Eccezioni:

* runbook operativi;
* contratti API con più endpoint;
* roadmap pianificate;
* documenti con schema dati o matrice test.

Quando un file supera circa 700–900 parole, verificare se contiene più responsabilità e se deve essere diviso.

Non dividere un documento soltanto per ridurre il numero di parole.

## Struttura standard

Ogni documento tecnico usa, quando applicabile:

```txt
meta
→ Scopo
→ Stato
→ Responsabilità o flusso
→ Contratti o invarianti
→ Confini
→ Verifica
→ Documenti collegati
```

Non tutte le sezioni sono obbligatorie.

Un documento piccolo può omettere le sezioni non utili.

## Stato

Usare soltanto stati espliciti:

| Stato                       | Significato                                              |
| --------------------------- | -------------------------------------------------------- |
| `Implementato`              | Codice e comportamento esistono                          |
| `Implementato, da validare` | Codice presente ma non validato su casi reali rilevanti  |
| `Pianificato`               | Contratto desiderato; file o feature non esistono ancora |
| `Deprecato`                 | Non usare per nuove modifiche                            |
| `Legacy`                    | Conservato solo per confronto o migrazione               |

Non chiamare “implementata” una policy soltanto perché è documentata.

## Naming e ordine

Usare:

```txt
01-nome-chiaro.mdx
02-nome-chiaro.mdx
```

Regole:

* numerazione locale alla cartella;
* nomi in kebab-case;
* titolo umano nel campo `meta`;
* niente file generici come `misc.mdx`, `notes.mdx` o `todo.mdx`;
* niente capitoli aggregatori come fonte di verità.

## Link relativi

I link devono puntare al documento canonico più specifico.

```md
[Source Identity](../modules/evidence/02-source-identity.mdx)
```

Prima di salvare un file, verificare:

```txt
percorso relativo corretto
→ file destinazione esistente
→ nessun link al vecchio sections/ se esiste il modulo nuovo
→ nessun link circolare inutile
```

## Percorsi e fatti tecnici

Documentare soltanto percorsi, endpoint, opzioni CLI e comportamenti verificati nel codice.

Quando un percorso o una feature è proposta, indicarlo esplicitamente:

```txt
proposto
pianificato
da implementare
da validare
```

Non inventare route, cartelle o test come se esistessero.

## Codice e segreti

Non inserire nella documentazione:

* cookie;
* token;
* password;
* API key;
* profile directory personali;
* header sensibili;
* dump di rete;
* payload reali contenenti dati sensibili.

Usare placeholder sicuri:

```txt
<eventId>
<betfair-url>
<profile-dir>
<cdp-url>
```

## Contesto per API AI

Le regole su quale contesto fornire a un’API AI hanno un’unica fonte canonica:

[Selezione del contesto per API AI](./01-context-selection.mdx)

Questo documento non ripete quella policy. La documentazione deve però restare sufficientemente modulare da permettere la selezione di un file di modulo, di un contratto collegato e del test più vicino senza dover inviare capitoli aggregatori o l’intero repository.

## Aggiornamento obbligatorio

Aggiornare un documento quando cambia:

* ownership di un modulo;
* endpoint, payload o status HTTP;
* argomento CLI;
* comportamento di persistenza;
* invarianti di Source Identity;
* comportamento runtime;
* test rilevante;
* stato implementato o pianificato;
* percorso di file canonico.

Non aggiornare documentazione per rinominare codice senza verificare tutti i link in ingresso.

## Verifica documentale

Prima di considerare una modifica documentale conclusa:

```txt
[ ] Il file è salvato nel percorso corretto.
[ ] Il meta è valido.
[ ] Il documento ha una sola responsabilità.
[ ] I link relativi sono validi.
[ ] Non esiste un duplicato del contratto in un altro file.
[ ] I percorsi e i fatti tecnici sono verificati.
[ ] Lo stato è corretto.
[ ] Non sono presenti segreti o dati sensibili.
[ ] Nessun aggregatore è usato come contesto API senza necessità.
```
