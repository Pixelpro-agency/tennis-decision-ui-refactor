# Stato attuale e priorità

## Scopo

Questo documento separa funzionalità implementate, validazioni ancora aperte e lavoro pianificato.

Non è una lista di desideri. Ogni priorità deve preservare timeline e history canoniche, confini modulari e contratti già esistenti.

### Contesto locale V1

**Implementato, da validare su match reale.**

Il contesto locale usa dati SofaScore normalizzati per mostrare:

```txt
punti nel match
→ ultimi tre game completati
→ differenza osservata rispetto al match
→ data quality
```

La finestra recente è disponibile soltanto quando le transizioni point-by-point sono verificabili e include esattamente tre game completati, con il game corrente escluso.

`comparison` e `observedShift` sono descrittivi. Non rappresentano trend, previsione, fair odds o segnale operativo.

### Task 3a completato

Lo stop globale del live tracking e il cleanup backend su `SIGINT` o `SIGTERM` sono implementati e validati live.

### Task A — launcher locale sicuro e automatico

**Implementato, con verifica live parziale.**

Il launcher non termina processi in base alla sola porta. Riuso, manifest runtime e shutdown restano limitati ai servizi identificati e ai processi owned dalla sessione. Chrome/CDP, riusato o avviato dall’helper, resta escluso dalla ownership e non viene chiuso dal launcher.

Verificato live:

```txt
python avvio.py
→ backend avviato
→ frontend Vite avviato
→ browser aperto dal launcher
```

Il falso timeout frontend causato dal wrapper batch npm è stato corretto.

Restano da validare live:

```txt
porte backend e frontend preferite occupate da processi esterni
→ fallback su porte alternative

doppio avvio ravvicinato

Ctrl+C
→ arresto dei soli processi owned

CDP alternativo su porta diversa da 9222
```

### Task 4 completata e validata

La persistenza delle timeline SofaScore e Betfair è ora centralizzata in `timelineStore.js`. L’helper tecnico interno `writeTimelineDocument(...)` esegue tutte le riscritture canoniche tramite documento completo in memoria, file temporaneo nella stessa directory e rename sul file canonico.

Non sono cambiati formato JSON, naming dei file, metadata, deduplicazione, sequenze, history aggregata o contratti HTTP, CLI e frontend.

La Task 4 è validata con i test di `timelineStore`, degli update SofaScore e Betfair e del lifecycle scraper Betfair. La verifica live ha confermato la continuità delle timeline dopo Stop e nuovo Start, senza file `.tmp` residui.

### Task 1A completata e testata

Task 1A introduce il Source Identity Gate tra polling live e persistenza canonica.

```txt
Nel tracking live coordinato:

collecting / pending
→ buffering in memoria
→ nessuna nuova timeline o history canonica della sessione corrente

recording
→ bootstrap SofaScore → Betfair
→ persistenza canonica

mismatch
→ tick causale bloccato
→ arresto di tutti i tracker attivi
→ preservazione del solo gate mismatch dell’evento causale
→ terminazione degli scraper Betfair figli del progetto
→ Chrome/CDP lasciato aperto
```

Il nuovo endpoint status è:

```txt
GET /api/match/:eventId/source-identity-status
```

Il bootstrap cross-source non è transazionale. Se SofaScore viene scritto e Betfair fallisce, il gate torna `pending` con:

```txt
Bootstrap persistence failed
```

### Task 1B implementata, da validare su pending reale

Task 1B collega il frontend al gate Source Identity live.

```txt

→ semaforo sidebar
→ presentazione della waiting screen, della modale pending e del toast
→ mismatch con ritorno al form
```

La waiting screen resta visibile finché il bootstrap frontend non ha prodotto `dashboardContentReady` e `dashboardData`.

La phase Source Identity determina testo, tono, modale e toast. Non sblocca direttamente la dashboard.

Verifiche live completate:

```txt
collecting
→ recording/aligned automatico

mismatch
→ ritorno al form con campi preservati

mismatch
→ correzione link
→ nuovo Start
→ aligned
```

Restano aperte:

```txt
pending reale
→ conferma manuale reale
→ recording/aligned

pending reale
→ decline
→ stop
→ ritorno al form
```

La UI usa soltanto il pending comunicato dal gate backend.

La validazione non prevede più una simulazione client-side.

La conferma manuale su pending reale non è ancora verificata live: le coppie disponibili finora hanno restituito mismatch dal backend.


### Task 6 completata — commit journal, recovery e persistence integrity

Task 6 introduce il contratto di persistenza journalizzata senza cambiare il ruolo canonico di history e timeline.

```txt
campione valido
→ commit canonico journalizzato
→ history + timeline
→ integrity read-only
```

Implementato nel contratto operativo corrente:

```txt
commitId canonico
pending_commits come sidecar tecnico
recovery deterministica di commit incompleti
repairOnly Betfair su journal pending
integrity additiva read-only per Match e Betfair
persistenceComplete:false per Evidence
no-trade reason per persistenza incompleta
UI degradata senza recovery frontend
retention e rollback che non cancellano journal pending
```

Gli stati di persistenza incompleta sono:

```txt
partial_persistence
recovery_failed
```

Questi stati non sono Source Identity mismatch, freshness stale, Graph health degradato, errore CDP, errore runtime scraper o segnale Money Flow.

Le route read-only non eseguono recovery, non scrivono journal, non avviano tracker o scraper e non mutano `marketState`.

### Hardening diagnostica e configurazione Betfair

**Implementato, da validare su runtime reale.**

La chiave applicativa Betfair è risolta da `BETFAIR_APP_KEY` nell’ambiente o dal file `.env` locale della root, senza valore letterale nei file Python.

La redazione diagnostica copre log, errori, dump di rete, output scraper, cache Betfair e bridge Node/Python.

Verificato offline:

```txt
test configurazione Betfair
test redazione diagnostica
test cache Betfair
py_compile Python
node --check runner/fetch
test lifecycle Node/Python
probe locali con marker fittizi
```

Resta aperta la validazione controllata su diagnostica runtime reale con Chrome/CDP e Betfair, senza condividere segreti, cookie, dump o payload reali.

### Retention cache runtime offline

**Implementato, da validare.**

È disponibile una utility standalone:

```txt
scripts/cleanup_runtime_cache.py
```

La utility opera solo sulle cache runtime allow-list:

```txt
backend/betfair_cache
backend/scraper_cache
```

Il dry-run è verificato. Il percorso reale `--apply --offline-confirmed` non è ancora validato operativamente su cache reali.

Non esistono job schedulati, cron, avvio automatico dal launcher o cleanup periodico.

## Attività da non anticipare

Non anticipare:

* previsioni di vincitore;
* attribuzioni di smart money;
* causalità fra campo e mercato;
* fair odds non calibrate;
* segnali automatici di trading;
* cancellazione di timeline o history canoniche;
* cancellazione manuale di `pending_commits` per risolvere errori di persistenza;
* recovery da API read-only, diagnostica o frontend;
* interpretazione di `partial_persistence` o `recovery_failed` come Source Identity mismatch, freshness stale, health Betfair o segnale operativo;
* refactor estesi durante validazione live incompleta;
* persistenza Market Reactions senza regole di deduplicazione;
* backtest basati su snapshot latest o dump browser.

## Criteri per aprire una nuova feature

Una nuova feature deve avere:

```txt
obiettivo misurabile
→ owner del modulo
→ input canonici
→ confini espliciti
→ test più vicino
→ comportamento con dati mancanti
→ comportamento con persistenza incompleta nota
→ nessuna dipendenza da segreti o dump
```
