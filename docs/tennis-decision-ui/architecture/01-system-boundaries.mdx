# Confini del sistema

## Scopo

Questo documento definisce i confini fra frontend, backend Node, package Python, persistenza e fonti esterne.

Usarlo prima di spostare responsabilità fra moduli o modificare un contratto che attraversa più livelli.

## Flusso principale

```txt
utente
  ↓
frontend React / Vite
  ↓ HTTP /api
backend Express
  ├─ servizi di tracking, Evidence e persistenza
  └─ wrapper Python compatibili
      ↓
      package scrapers/
      ↓
      SofaScore, Betfair e Chrome CDP
```

Il runtime locale segue un percorso distinto:

```txt
avvio.py
  ↓
launcher/
  ↓
Chrome CDP + backend Express + frontend React / Vite
```

I dati live e persistiti attraversano due fasi distinte:

```txt
campioni live SofaScore + Betfair
  ↓
Source Identity Gate in memoria
  ├─ collecting / pending
  │   └─ ultimo campione valido per fonte, nessuna scrittura
  ├─ recording / not-applicable
  │   └─ persistenza canonica autorizzata
  └─ mismatch
      └─ persistenza bloccata e tracking fermato
  ↓
timeline SofaScore + timeline Betfair + history aggregata
  ↓
Match Evidence Snapshot
  ↓
frontend / analisi futura / replay
```

## Proprietà dei confini

| Livello           | Proprietario                                                | Responsabilità                                                                                                        | Non deve fare                                                |
| ----------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Frontend          | `frontend/`                                                 | Sessione UI, polling HTTP, rendering, input operatore                                                                 | Accedere a file locali, avviare Python, ricostruire Evidence |
| API               | `backend/src/routes/`                                       | Contratto HTTP, validazione richiesta, adattamento Express                                                            | Contenere logica di dominio duplicata                        |
| Tracking          | `backend/src/sofa/matchTracker.js`, `sourceIdentityGate.js` | Scheduler, concorrenza, gate Source Identity, stop e polling separato                                                 | Gestire dettagli HTTP o UI                                   |
| Dominio           | `backend/src/sofa/`                                         | Normalizzazione, Evidence, identity, flow, allineamento                                                               | Dipendere da componenti React                                |
| Persistenza       | `matchHistory.js`, `timelineStore.js`                       | History, timeline e scrittura atomica                                                                                 | Avviare scraper o dedurre strategia                          |
| Adattatori Python | wrapper root e package `scrapers/`                          | Accesso a SofaScore, Betfair, browser e CDP                                                                           | Esporre dettagli browser al frontend                         |
| Runtime           | avvio.py, `launcher/`, `scripts/`                           | Avvio locale, riuso di servizi identificati, selezione non distruttiva delle porte e shutdown dei soli processi owned | Decidere regole di dominio o terminare processi esterni      |

## Invarianti

* Il frontend comunica con il backend tramite `/api`; non chiama direttamente scraper Python o filesystem.
* I router sono il confine HTTP pubblico. Un refactor interno non cambia metodo, endpoint, payload o status senza una modifica dichiarata del contratto.
* SofaScore e Betfair hanno polling e failure mode indipendenti.
* Le timeline raw sono la fonte cronologica primaria; Evidence le legge senza modificarle.
* Gli endpoint read-only non avviano scraper, tracking, browser o scritture nelle timeline.
* I wrapper root `avvio.py`, `scraper.py` e `betfair_scraper.py` restano compatibili finché esistono chiamanti esterni.
* Il runtime non termina processi in base alla sola porta. Può riusare un servizio solo dopo verifica di identità; shutdown e fallback agiscono soltanto sui processi owned dalla sessione. Chrome/CDP esterno resta fuori dalla ownership.
* Network dump, cache browser e profili Chrome non sono fonti algoritmiche.
* Source Identity Gate non riscrive timeline raw o history esistenti: autorizza oppure blocca esclusivamente le nuove scritture canoniche.

## Confini da rispettare durante un refactor

```txt
UI
→ API
→ servizio di dominio
→ persistenza o adattatore esterno
```

Non saltare livelli senza una ragione esplicita.

Esempi:

* una modifica alla UI Source Identity legge lo stato live dal router Match e invia la conferma manuale al router Evidence, senza accedere direttamente al confirmation store;
* una modifica alla route Betfair può delegare a un modulo puro, ma non incorporare lifecycle Python nel controller;
* una modifica allo scraper deve conservare CLI, JSON output e wrapper compatibili.
