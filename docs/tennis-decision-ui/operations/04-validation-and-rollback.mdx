# Validazione e rollback

## Scopo

Questo runbook definisce la sequenza minima dopo una modifica a codice o documentazione tecnica.

```txt
modifica piccola
→ controllo statico
→ test mirato
→ smoke test sicuro
→ verifica funzionale
→ controllo integrità persistenza quando coinvolta
→ rollback selettivo se necessario
```

## Regola principale

Non verificare l’intero progetto per una modifica locale.

Usare il test più vicino al modulo toccato, poi aggiungere solo i controlli necessari al confine attraversato.

## Matrice di verifica

| Area modificata                      | Controllo minimo                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Modulo Node puro                     | `node <file>.test.mjs`                                                                                     |

| Pipeline Betfair Task 2              | Due sessioni reali: Graph URL disponibili e assenti; record in `operations/07-betfair-live-validation.mdx` |
| Money Flow dashboard non direzionale | test read model API, validazione volume, utility frontend e build                                          |

| API HTTP                             | test modulo, test route, richiesta con input non distruttivo                                               |
| Documentazione                       | link relativi, percorsi reali, contratti coerenti                                                          |
| Source Identity Gate                 | test gate, tracker, route status, route Evidence e verifica live controllata                               |
| Hardening diagnostica Betfair        | unittest redazione/config/cache, `py_compile` Python, `node --check` runner/fetch e test lifecycle         |
| Retention cache runtime              | unittest utility cleanup, `py_compile`, dry-run JSON senza rimozione reale                                 |

La validazione live Task 2 è completata con rilievi documentati.

Non usare il report live per dichiarare verificati scenari non osservati: login scaduto, URL invalide, failure rete/API e mercato finished restano casi operativi distinti.

Per modifiche alla persistenza journalizzata non dichiarare validato il flusso finché non sono stati coperti almeno:

```txt
commit completo
commit partial
recovery riuscita
recovery_failed
lettura read-only di integrity
rollback senza cancellazioni cieche
```

La presenza di `partial_persistence` o `recovery_failed` è un esito di integrità della persistenza, non un errore di health, freshness, Source Identity, Graph URL, frontend o runtime scraper.

```txt
journal pending valido
→ recovery bootstrap tentata
→ complete o recovered
→ journal rimosso solo dopo target verificati

journal invalido ma identificabile
→ recovery_failed osservabile
→ backend avviabile se errore per-file non fatale

journal non sicuro o non parsabile
→ invalidJournal
→ nessuna scrittura business
```

Per Betfair verificare inoltre:

```txt
sample tecnico non valido + journal pending
→ repairOnly consentito
→ nessun nuovo tick
→ nessuna nuova row history
→ nessuna mutazione marketState

complete o recovered
→ runtime state confermabile

partial, failed, writer non-ok o commitId errato
→ runtime state non confermato
```

Non creare manualmente file parziali sotto `backend/match_history/` in una sessione live. La validazione va fatta con fixture o ambiente controllato.

## Vincoli di rollback Task 2

Il rollback non deve cancellare `pending_commits`, history o timeline; non deve terminare processi esterni, usare kill per porta o ripristinare fallback CDP impliciti.

## Rollback

Il rollback deve essere selettivo.

```txt
fermare il servizio interessato
→ identificare il file coinvolto
→ ripristinare solo la versione nota come funzionante
→ eseguire controlli statici
→ eseguire test mirati
→ riavviare solo il servizio necessario
→ verificare il flusso interessato
```

Per wrapper Python compatibili, `legacy/` può essere una fonte di confronto. Non ripristinare un’intera cartella se il problema riguarda un solo file.

### Rollback della persistenza journalizzata

Il rollback di codice che tocca journal, history o timeline non deve cancellare dati canonici per nascondere un partial.

Sequenza sicura:

```txt
fermare il writer interessato
→ preservare history, timeline e journal esistenti
→ identificare il commitId o l'eventId coinvolto
→ classificare lo stato come no_known_partial, partial_persistence o recovery_failed
→ ripristinare solo il codice coinvolto
→ rieseguire test mirati su fixture
→ avviare bootstrap recovery controllata
→ verificare payload read-only di integrity
```

Non fare rollback manuale tramite:

```txt
cancellazione cieca di .pending_commits
cancellazione di timeline
cancellazione di history
editing manuale di completed marker
editing manuale di commitId
ricostruzione da runtime state
ricostruzione da frontend
ricostruzione da Evidence
```

Un journal `completed` residuo può essere rimosso solo dal codice di cleanup previsto e soltanto dopo verifica dei target canonici.

Un journal `recovery_failed` è un dato diagnostico dell’incidente: conservarlo finché la causa non è stata capita o finché una procedura esplicita di retention non lo rimuove.

### Rollback API integrity

Se il problema riguarda solo payload pubblici di `integrity`, il rollback deve limitarsi a route, adapter di lettura o serializzazione HTTP.

Non modificare:

```txt
history
timeline
journal
commitId
payload di recovery
Source Identity confirmations
```

Un errore di redazione pubblica non autorizza la cancellazione del journal sottostante.

## Dati da non toccare

Durante verifica o rollback non modificare:

```txt
backend/match_history/
backend/match_history/.pending_commits/
timeline SofaScore e Betfair
journal sidecar
backend/source_identity_confirmations.json
profili Chrome
cookie
sessioni
segreti
file .env
dump utili a un incidente ancora aperto
log utili a un incidente ancora aperto
```

Non cambiare dati raw per fare passare un test.

## Invarianti

* Non eseguire modifiche durante tracking live attivo.
* Non usare endpoint distruttivi come smoke test.
* Non chiudere Chrome CDP come parte della verifica.
* Non sostituire test mirati con lettura log generica.
* Non fare rollback di file non coinvolti.
* Non dichiarare conclusa una modifica finché il flusso interessato non è stato verificato.
* Non cancellare journal pending o recovery_failed come parte di una verifica ordinaria.
* Non usare route read-only per eseguire recovery.
* Non esporre payload journalizzati, path locali o dettagli filesystem in risposte pubbliche.
* Non confermare `marketState` Betfair se il commit strutturato non è `complete` o `recovered`.

Per un partial di persistenza non modificare manualmente timeline, history o journal per forzare `no_known_partial`.

```txt
preservare i dati
→ classificare integrity
→ correggere il codice
→ ripetere i test mirati
→ validare bootstrap recovery o payload read-only
```

Per un tick Betfair duplicato o regressivo non modificare manualmente timeline o history per “rimuoverlo”.

```txt
correggere il codice
→ ripetere i test mirati
→ rieseguire la verifica controllata
```

Per una regressione del grafico Money Flow non direzionale, il rollback riguarda soltanto i file del read model API e della UI Task 2E.

Non ripristinare:

```txt
logica raw Back / Lay
scraper
timeline
Graph URL
health
```
